# 客户端「同值 tick 去重」：挡住了什么，又误伤了什么（2026-10-29 复核）

> 状态：**已按方案 A 移除**（2026-10-29，`MarketData/CtpMarketData.cs:181-200`：回调入口不再判重，每条都投递）。判定与实测保留在下面各节。
> 上游事实见 `../../ctp-net-front/doc/md-tick-delivery.md`（前置已按帧级去重，实测 0 次同帧重复投递）；tick 产生语义见 `../../aether-exchange/doc/tick-emission.md`。

## 1. 它原来的做法（代码已删除，2026-10-29）

`OnRtnDepthMarketDataCb`（当时的 `CtpMarketData.cs:186`）每收到一个原始回调，先组 `TickData`，再问 `SuppressDuplicate`：

```csharp
private static bool SameContent(in TickData a, in TickData b) =>
    a.LastPrice == b.LastPrice
    && a.Volume == b.Volume
    && a.OpenInterest == b.OpenInterest
    && a.Turnover == b.Turnover
    && a.BidPrice == b.BidPrice && a.BidVolume == b.BidVolume
    && a.AskPrice == b.AskPrice && a.AskVolume == b.AskVolume;
```

三条性质值得写下来：

| 性质 | 后果 |
|---|---|
| **`UpdateTime` / `UpdateMillisec` 不参与比较** | 「内容相同、时间不同」的**两个不同事件**被判为重复 |
| **只比每个合约的上一笔已投递 tick**（`_lastDelivered`） | A→B→A 时 A 正常通过；它其实没有「判重」的定义，只有「和上一笔一样就丢」 |
| **丢弃发生在回调里、在 `TickReceived` 之前** | 订阅者永远看不到被丢的帧，也没有任何旁路信号说明「这期间市场发生过变化」 |

另外，帧模板里没有成交额槽（`BuildMdTick` 的 Edit 列表只写 交易日/合约/时间/最新价/成交量/持仓量/买一/卖一 8 个槽），`Turnover` 对每条 tick 都是同一个模板常量 ⇒ **8 个比较项里有 1 项恒真**，不产生任何判重能力。

## 2. 实测：它丢的全是真实事件

采样方式：`AETHER_CTP_TICK_TRACE=1` 打开逐笔日志，打印点在**去重之前**（`CtpMarketData.cs:189`），所以能看到「进来多少条、被丢掉哪几条」。

| 采样 | 原始回调 | 重复投递（时间 + 6 个量价槽全同） | 被本层丢弃（内容同、时间不同） |
|---|---|---|---|
| 43 秒（13:55:30–13:56:13） | 1014 | **0** | 1（订阅快照帧，`volume=0`） |
| 5 分钟（13:57:38–14:02:40） | 382 | **0** | **11**（占 2.9%；最长连续丢 3 帧） |

（判据：逐笔日志覆盖帧内 8 个可变槽中的 7 个——缺持仓量；真·重复帧逐字节相同，必然命中这 7 项，所以第一列是可靠下界。）

第二列是判据：**同一帧从来没被重复投递过**（前置的逐字节去重已经兜住了，见上游文档 §5）。所以本层「有重复就吞掉」这个存在前提，在这条链路上是不成立的。

第三列逐条对过：11 条全部是「`UpdateTime` 的秒在前进，其余 8 个量价字段完全一致」。这就是做市商在第 2 档以下撤改、买一卖一与累计成交量均未变化时产生的**合法快照**（上游文档 §3）。丢掉它们，等于宣告「市场这段时间没动过」——而事实是簿在变、时间在前进。

### 自己生成的告警是恒误报

`CtpMarketData.cs:232` 那行日志的判词是：

```
[ctp-md] 同值 tick 去重 N 条/10s（累计 M）——非零说明上游在重复投递，排查客户端会话重建/原生层重放
```

按上面的数据，**在完全干净的上游上它一样会涨**（11/382）。一条「只在故障时该出现」的告警，如果能被正常行情触发，它就不是告警，是噪音——而且会把人引向「查客户端会话重建」这个错误方向。

## 3. 真实的交易客户端怎么处理这件事

分三层看，**没有一层是在「按内容判重」**：

| 层 | 真实做法 | 为什么 |
|---|---|---|
| **API/网关层**（CTP `OnRtnDepthMarketData`、vn.py 的 CTP gateway、QuickFIX 类封装） | 每个回调**逐条**转给上层，不去重 | 网关不知道订阅者想怎么用；快照流没有序号，任何丢弃都**不可验证**、不可重放 |
| **终端渲染层**（快期、博易、文华类看盘软件） | **合并重绘**：回调线程只记「每个合约的最新一笔」，按帧率（10–60 Hz）刷一次界面 | 这才是「重复帧」真正该被吸收的地方——因为吸收的是**渲染**，不是**数据** |
| **策略层** | 每条都过一遍，策略自己决定要不要用 | 判断依赖的不只是 8 个价格字段（例如「时间戳不动 = 数据源可能挂了」就是靠每条 tick 的到达） |

本仓的桌面端**已经是第三种写法**：`MarketWatchViewModel`（`../../aether-ctp-desktop/src/Aether.CtpDesktop/MarketWatch/MarketWatchViewModel.cs:86-121`）用 `ConcurrentDictionary` 记每合约最新一笔 + 1 秒 `DispatcherTimer` 合并刷新，注释里写得很清楚——这正是 2026-10-29 那次卡死后该补的那一层。**它已经解决了刷屏，库层再去重就是重复劳动，代价是丢数据。**

## 4. 它还会自己制造「假死」

2026-10-29 那次事故的判据之一是「盘口时间戳停在同一毫秒」。有了这层去重，只要行情变成「只做第 2 档以下撤改」，界面上显示的 `UpdateTime` 就会**停在最后一个内容变化的秒上**——症状与「数据源挂了」一模一样，但数据其实一直在来。

换句话说：**它为防一种症状，自己造了同一种症状。** 这比不做多了一层不可观测性。

## 5. 它也挡不住真正该挡的东西

真正需要防的是 2026-10-29 的 native 层重放：2.82M 次回调/10 秒、只有一种字段组合、前置日志 10 秒只涨 13 字节。那种情况下：

- **同一个帧会被反复投递**，`UpdateTime` 也是同一个 ⇒ 前置的逐字节去重会把除第一帧以外的全部吞掉，客户端根本收不到风暴；
- 就算漏进来（会话重建首帧），正确的判据是**速率**（每秒回调数 / 每秒唯一帧数），不是「和上一笔内容相同」。

拿「内容相同」当风暴判据，等于用暖炉测火灾。

## 6. 处置方案（**A 已实施**）

| 方案 | 改动 | 评价 |
|---|---|---|
| **A. 删除本层去重**（✅ 已实施） | 去掉 `SuppressDuplicate` 调用与 `_lastDelivered`，保留 `AETHER_CTP_TICK_TRACE` 逐笔日志 | **推荐并已采用**。上游已有帧级保证，下游桌面端已有合并刷新；删掉就恢复「每条回调必达」的契约，简单可验证 |
| B. 键里加上时间 | `SameContent` 增加 `a.UpdateTime == b.UpdateTime && a.UpdateMillisec == b.UpdateMillisec` | 折中：保留「同帧重放」防护，误伤消失；但仍是不可观测的静默丢弃，且与前置重复 |
| C. 保留计数、不丢帧 | 命中时计数并打日志，但仍然 `TickReceived?.Invoke` | 最小改动：立刻消除误伤和数据盲区，代价是把「重复」压力交给订阅者（桌面端已经能承受） |

无论选哪个，**告警文案要改**：不能再说「非零说明上游在重复投递」。若保留计数，正确说法是「内容相同但时间前进的连续快照数」——它是行情活跃度的一个侧写，不是故障信号。

风暴检测单独做：按 `会话` 统计每秒回调数，超过阈值（例如 10× 平均）才告警。

## 7. 验收（2026-10-29 实测结果）

改完后用**桌面端**（md-only 客户端，连远程前置 `117.72.186.128:17802`）跑了两段：

| 段 | 时长 | 原始回调 | 逐字节重复 | 内容同/时间不同（旧构建会丢） | 行情 |
|---|---|---|---|---|---|
| 第一段 | 2 分 14 秒 | **110** | 0 | **5（已全部投递）** | `last` 99.9531–100.0469（6 个价位），`vol` 2369→2456（+87 手） |
| 第二段 | 约 50 秒 | **12** | 0 | 0 | 同一秒内连出数帧（只改买一/卖一档量），逐帧都在 |

第二段同时做了**端到端 1:1 核对**（同窗口计数）：

```
前置日志 pushlines: 42939 → 42950   ⇒ 窗口内推送 11 帧
桌面端 Tick 行:                     12 条
差额 1 = 订阅快照帧（前置记作「快照」，客户端按 tick 帧收到）
```

即：**前置推了 11 帧、客户端交付 12 次回调（11 + 1 快照），零丢失**——这正是本层移除后要的契约。
旧构建在同窗口内会额外吞掉「内容相同、时间前进」的帧。

回归自检（以后要重复的话）：

```bash

AETHER_CTP_TICK_TRACE=1 <客户端程序>
# 期望：每条回调一行；旧的那行「同值 tick 去重 N 条/10s」已不存在
```
